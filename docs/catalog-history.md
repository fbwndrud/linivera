# 기능·접근 카탈로그 판본 보존

명세 ID는 정확한 출고 판본이다. `local-broker-v1` 같은 ID를 최신 값의 별칭으로 쓰지 않는다.
JSON의 `version: 1`은 기록 스키마 버전이며 ID 접미사의 판본 번호와 별개다.
동일 ID의 입력·출력·identity뿐 아니라 확인일·공식 근거·미확인 설명도 불변이다.

## 추가 전용 출고 절차

1. 기존 ID와 내용, `catalog-release-v1.js` 등 출고 hash 파일을 보존한다. 항목을 삭제하거나
   기존 ID를 다시 pin하지 않는다. 날짜나 근거만 바뀌어도 기존 내용을 덮어쓰지 않는다.
2. 변경은 새 ID(예: `local-broker-v2`)의 전체 명세를 카탈로그에 추가한다. 접근 명세도 새 ID로
   추가하고 정확한 `capabilityId`에 결속한다. 예전 접근·기능 명세도 계속 조회 가능해야 한다.
3. 새 출고 파일에는 새 ID의 canonical JSON SHA-256만 추가한다. `catalog-releases.js`의
   목록에 그 출고 파일을 추가한다. 과거 출고 파일을 수정해 새 내용을 승인하지 않는다.
4. 새 판본의 validator·실행 가능 범위와 공식 근거를 검토한다. 새 ID를 추가한 것만으로
   공급자 기능·권한·credits 또는 실행기 지원을 선언하지 않는다.
5. 실제 MCP와 설치 tarball에서 구/신 ID 조회, 과거 명세·보고·Input/hash 검증, 신규 요청
   계약 검사를 실행한다. 새 보고·Input을 만들되 예전 판본을 자동 교체하지 않는다.

`catalog-registry.js`는 출고 hash와 카탈로그 전체를 시작 시 대조한다. 기존 항목 삭제·내용
교체·중복 ID·기존 ID 재출고·hash 없는 새 판본을 거절한다. 조회는 정확한 ID만 받으며
보관 내용의 복사본을 반환한다. 이 검사를 끄는 호스트 설정·공개 MCP 입력은 없다.
출고 v1 hash 집합도 golden 회귀로 고정한다. 소스와 hash를 함께 바꿔 역사 판본을 지우는
변경은 정상 업그레이드가 아니며, 별도 호환성 변경으로 검토해야 한다.

## 보고 알고리즘과 역사 읽기

카탈로그 판본과 보고 알고리즘 버전은 별개다. capability-readiness v1/v2는 각각 당시 계약으로
과거 기록 prefix에서 재계산한다. 앞으로 판정 의미나 보고 필드를 바꾸면 새 보고 버전과
명시적 replay 분기를 추가하고 기존 버전의 동작을 보존한다. 공유 validator 변경도 과거
replay에 영향을 주므로 골든 hash·과거 Input 회귀를 통과해야 한다.

역사 검증 성공은 현재 실행 허가가 아니다. 새 Input·Operation·현재 연결 점검·공식 도구
prepare에는 현재 요청·scope·선택·만료·권한 잠금이 적용된다. 구 보고를 만들거나 구 명세를
선택해 현재 차단을 우회할 수 없다. 과거 데이터에 대한 별도 실패가 필요하면 기록을 지우는
대신 현재 실행 guard로 표시한다.

여기서 요청 계약은 사용자가 선택한 정확한 명세 ID에 대한 현재 validator다. 새 ID의 더 좁은
조건을 구 ID에 소급 적용하거나 자동으로 최신 ID를 선택하지 않는다. 새 판본이 추가됐다는
이유만으로 구판 실행을 폐기하지 않는다. 폐기가 필요하면 구판 보관·역사 읽기를 유지하면서
현재 실행 guard에 별도 사유를 추가해야 하며, 출고 항목 삭제로 대신하지 않는다.

범위는 저장소에 출고한 정적 명세다. 원격 공급자 문서를 자동 갱신하거나 임의의 사용자
명세를 공식 카탈로그에 등록하는 API는 제공하지 않는다. 실제 계정과 공급자 실행 검증은 별도다.
