# Chroma P0~P4 보관·연결·재사용 점검

점검일: 2026-10-23. 구현 기준: `49f4dcf0235abc492f1c5ba1db5cec46d8f822a3`.
신규 구조 연결의 고정 비교 범위는 `git diff 129fc24...49f4dcf`의 12개 커밋,
87개 파일이다. 앞선 공통 반입·보관·Input·Operation 경로도 코드와 관련 테스트로 확인했다.

## 판정

**확보한 파일을 정확한 판본으로 보관하고, 명시적으로 연결하여 다음 작업에 쓰는
공통 경로는 구현되어 있다.** 전용 파서가 없는 자료도 파일·bundle·명시적 사용 맥락으로
연결할 수 있다. 원본을 교체하면 과거 Input은 유지하고 그 원본을 사용한 후속 결과는
재검토 대상으로 표시한다.

다만 모든 파트너의 데이터를 자동 확보·해석하거나, 결과물 하나를 선택했을 때 관련
브리프·권리·공급자 이력을 모두 자동으로 입력에 넣는 상태는 아니다. 각 단계의 연결은
검증했지만, P0~P4를 하나의 작업 공간에서 끝까지 연결한 통합 검증은 남아 있다.

## 우선순위와 다음 수용 기준

### 1. 다음 작업에 넘길 맥락을 한 묶음으로 고정

현재 `performance-map`을 선택하면 `release-map`과 배포 대상·증거가 Input에 포함된다.
그러나 같은 결과물을 가리키는 brief/rights/provider-response map은 역방향으로 자동
포함되지 않는다. P4 예제도 이 map들을 입력 roots로 각각 명시한다.
따라서 “파일이 연결되어 있다”와 “다음 작업에 필요한 맥락이 선택되어 있다”를 구별해야 한다.

기존 `usage-context`/`context-package`를 사용하여 결과물·공급자 응답·브리프·권리·편집/
프로젝트·배포/성과의 정확한 판본을 작업 목적에 맞게 묶는 경로를 우선 검증한다.
모든 역방향 관계를 무조건 자동 포함하면 이야기/경로 격리와 입력 용량을 침범할 수 있다.

수용 기준: 묶음 하나로 필요한 자료가 고정되고, 필수 맥락이 빠지면 명시적으로 드러나며,
권리 원문이나 upstream 자료 변경이 두 단계 뒤 결과까지 재검토를 요구해야 한다.
다른 이야기/경로의 자료는 중첩된 P3/P4 map을 통해서도 들어올 수 없어야 한다.

근거: [Input 폐쇄](../../core/resources/input-closure.js)의 typed actual-input 규칙,
[delivery 예제](../../examples/delivery-continuity.js)의 명시적 roots.

### 2. 하나의 작업 공간에서 P0~P4 전체 반복 검증

현재 structure/timeline/project/delivery 예제는 각각 새 임시 작업 공간을 만든다.
각 단계의 성공만으로 전체 조합의 성공을 입증할 수는 없다.

수용 기준: 합성 공급자 응답/파일 → workflow/model → 편집/프로젝트 → brief/rights →
release/performance → 다음 반복을 같은 작업 공간에서 실행한다. 중간 MCP 재시작,
원본 삭제 후 바이트 읽기, 정확한 판본·선언·증거의 Input 포함, 두 단계 변경 전파,
과거 Input 검증, 필수 연결 누락 차단과 별도 scope 격리를 함께 검사한다.
이 테스트의 후속 출력이 어떤 실제 바이트/구조 값을 소비했는지도 명시한다.

### 3. 실제 확보 경로와 원격 결과물 대응 증거

공통 브로커 계약은 호스트가 확보한 로컬 파일을 받는다. 모든 사이트의 계정 접근,
polling, 인증 복구, 만료 URL 다운로드를 제공하는 범용 네트워크 연결기는 아니다.
구조 binding은 보관 판본을 요구하지만 원격 ID/URL과 그 파일이 실제로 같은 결과물인지
자동 증명하지 않는다.

수용 기준: 실제 사용하는 대표 공급자부터 응답/job/file ID와 다운로드 파일의 대응을
확인한다. 공급자가 제공한 hash/영수증이 있으면 보존하고, 없으면 확인 주체와 근거를
기록한다. 중단·부분 다운로드·재시도·URL 만료 및 보관 전 호스트 재시작도 확인한다.
실계정 검증 자료는 저장소에 커밋하지 않는다.

### 4. 실제 제작에서 필요한 세부 의미와 복원

Aseprite tag 범위는 원본 값으로 보관하지만, 선택 export가 frame 번호를 바꿀 수 있어
tag↔export frame 소속을 추정하지 않는다. 명시적 대응 자료가 필요하다.
그 밖의 네이티브 편집/엔진/DB/환경은 파일과 의존성 증거를 보관·연결할 수 있으나 실행
복원까지 검증하지 않았다. 우선 사용하는 제작 도구의 export를 기준으로 보완한다.

미디어 검증은 주로 보관 바이트·hash·구간·JSON 값의 소비를 확인한다. P4 영상은 opaque
합성 fixture이며 실제 렌더·재생·상용 플랫폼 게시를 검증한 결과가 아니다. 권리 보고는
원문과 연결되지만 원문 해석이나 법적 유효성·지표 진위의 자동 승인은 제공하지 않는다.

### 5. 반영 상태와 운영 규모 확인

점검 시 GitHub의 [PR #2](https://github.com/fbwndrud/linivera/pull/2)부터
[PR #8](https://github.com/fbwndrud/linivera/pull/8)까지 모두 open·미병합이다.
현재 설치한 MCP가 이 구현을 사용하는지는 확인하지 않았다. 사용 반영 단계에서는
의존 순서에 따른 병합과 설치 버전/commit 확인 후 같은 합성 MCP 시나리오를 실행해야 한다.
이번 점검에서 병합·배포는 수행하지 않았다.

파일당 2GiB, bundle 8GiB/4,096개와 구조 해석·Input 용량 제한이 있다.
허용 최대 크기의 성공 처리 시간/메모리, 다른 기기로 작업 공간을 옮긴 복구는 미검증이다.
bundle materialize는 manifest를 반환하며 편집 프로젝트 폴더 전체를 복원하는 기능이 아니다.
37개 파트너 명단은 2026-10-22 조사 기준이다. 공식 팩 재조회는 HTTP 403으로 실패하여
현재 명단과 모든 파트너의 실제 export 가능 여부를 다시 확인하지 못했다.

## Standards

문서 규칙 위반 **0건**, 수정이 필요한 설계 냄새 **0건**.
변경 코드의 300줄 초과, core/packs 네트워크 호출, hash·영수증·추가 전용 기록·잠금
우회를 발견하지 못했다. 원본·binding·별도 선언의 Input 폐쇄와 격리, release 원문 재계산과
플랫폼/계정/외부 ID 대조, 과거 파서 검증과 신규 작업의 구버전 차단을 확인했다.
추가 합성 공개 경로 검사에서도 provider-response 원문에 다른 경로의 usage-context를
연결하여 끌어오는 시도는 `CONTEXT_SCOPE_MISMATCH`로 차단됐다.

## Spec

재현한 신규 구현 오류 **0건**, 약속한 개별 계획의 필수 범위 누락 **0건**.
검증 빈틈은 전체 단계 통합, 중첩 P3/P4의 별도 scope, 실제 미디어/공급자/복원 경로다.
다음 사용 흐름의 핵심 빈칸은 브리프·권리·공급자 이력까지 묶는 입력 선택이다.
지원표 하단 자동 해석 총괄 문장이 P2까지만 열거하는 문서 불일치 **1건**을 발견해
이번 점검에서 P3/P4 범위까지 맞췄다. 나머지 항목들은 현재 기본 계약 위반과 구분하여
위 수용 기준으로 후속 작업한다.

검토 집계: Standards 0건. Spec 신규 구현 오류 0건·문서 불일치 1건 수정이며,
가장 먼저 보완할 사용 흐름은 맥락 묶음과 단일 작업 공간 통합 검증이다.
